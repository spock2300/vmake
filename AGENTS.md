# VMake agent guide

VMake builds C/C++ projects from Go scripts interpreted by yaegi. The Go executable and the projects it builds have separate build/test workflows.

## Build and verify

Requires Go 1.26+ (`go.mod`). Use CGO-disabled builds, including Windows cross-compiles. From the repository root:

```bash
CGO_ENABLED=0 go build -o vmake ./cmd/vmake
CGO_ENABLED=0 go vet ./cmd/vmake/... ./pkg/... ./internal/...
CGO_ENABLED=0 go test ./cmd/vmake/... ./pkg/... ./internal/...
```

- Never use bare `go test ./...` or `go vet ./...`: they traverse C/C++ fixtures containing Go buildscripts and fail with C-source errors.
- Focus a package/test with, for example, `CGO_ENABLED=0 go test ./pkg/api -run '^TestYaegiSymbolsComplete$' -count=1`.
- Rebuild `vmake` (`CGO_ENABLED=0 go build -o vmake ./cmd/vmake`) after changing exported symbols in `pkg/api`, `pkg/toolchain`, or `pkg/plugin`. Build scripts and plugins are interpreted against the symbol tables compiled into the running binary, so a stale `./vmake` ignores those changes.
- Run each integration project from its own directory: `(cd test_data/01_simple_c && ../../vmake build)`. Do not invoke a build from the `test_data/` parent.
- Firmware fixture 17 is in `test_linux/17_firmware`, not `test_data/`.
- Windows cross-build: `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -o vmake.exe ./cmd/vmake`.
- The Windows workflow (`.github/workflows/windows.yml`) runs only on manual `workflow_dispatch`, not on push or pull_request; it runs the scoped vet/test commands above with `-skip '(?i)subgraph|TestDeclarePackageTargetsDryRunWiring'` and leaves snapshots disabled. Run Linux/macOS verification locally.
- `build`/`rebuild` publish `build/vmake-build.json` and `test` publishes `build/vmake-test.json` (schemaVersion 2: command, status, duration, concise error, parsed diagnostics, success summary/counts, per-target status/duration/size, test results and hashed installed artifacts); `clean`/`distclean`/`pkg clean` remove both, and `clean` also removes the stale `build/compile_commands.json` and notes remaining other-configuration build keys. Reports are separate from `install/manifest.json`; see `docs/BUILD_RESULT.md`.

### Skill documentation loop

`cmd/vmake/skills/vmake/` is shipped documentation and must match the live CLI.

- `TestSkillCLIExamples` validates fenced `vmake` commands against the Cobra tree; the other `TestSkill*` tests check cross-references, API symbols, Go blocks, and removed CLI flags. Run them after any CLI or skill edit.
- After changing the embedded skill, rebuild `vmake` and run `vmake skill install` before testing an agent; editing the repository alone leaves the installed copy stale, and `vmake doctor` reports a stale or unversioned install (DD-35).
- Treat a fresh solver as the reward signal: give it a temporary project and only the installed skill, then check task success, `export PATH/CC/...` violations, and whether it can name the resolved compiler path. Fix the smallest doc cluster, rerun the same task plus a regression task, and revert changes that do not improve the result.
- `scripts/skill-loop/run.sh` automates this loop with solver, judge, author, and factcheck sessions; see `scripts/skill-loop/README.md` and `COVERAGE.md` before changing its tasks or reward. The `factcheck-*` tasks audit Markdown against code/CLI and are the detail-level regression signal.
- Skill content is limited to vmake behavior, its own requirements, and vmake-specific workflows. Do not add general OS/toolchain installation tutorials (Xcode/Homebrew/Ninja setup, distribution package advice); extra external knowledge is a burden for the agent.
- Product gaps (for example, there is no package/target build filter) must be documented as gaps, not papered over with invented flags.

### Build-behavior snapshots

`test_data/_snapshot` is a separate Go module. Rebuild the root `vmake` binary first; the tests execute it rather than compiling it themselves:

```bash
CGO_ENABLED=0 go build -o vmake ./cmd/vmake
(cd test_data/_snapshot && go test)
(cd test_data/_snapshot && go test -run '^TestSnapshotsTestData/01_simple_c$')
```

- Snapshots compare installed artifacts, a redacted manifest, and `build/compile_commands.json`. Use them for compilation/linking/install behavior changes.
- The harness deletes fixture-local build/install/dependency directories and `.vmake` configuration before and after each test. It sets an isolated `VMAKE_CACHE` and `VMAKE_TRUST_ALL=1`.
- Discovery is automatic for any top-level `test_data/*` directory containing a `build.go` at any depth. `skipProjects` excludes 07–10 and `skipProjectsDarwin` excludes ELF-only 12/22–24 on darwin; `TestSnapshotsTestLinux` adds firmware 17 when present.
- Prerequisites: 06 uses C++; 11 needs `official/tinyexpr`; 13 needs the `test_build` native repo; 25 requires `sh test_data/25_subpackage/setup.sh` after building vmake. That setup registers/trusts the local `subtest` repo in `~/.vmake`.
- For intentional drift, run `go test -update` inside `test_data/_snapshot` (optionally with `-run`). Only `baseline/` is committed; the code uses `baseline-windows/` or `baseline-darwin/` on those hosts, so create that directory before updating. Investigate drift before updating.
- CMake integration: `python3 test_windows/verify_cmake.py ./vmake` exercises real CMake/Ninja builds; `--arm` also requires the ARM toolchain. Windows ARM setup and verification commands live in that workflow.
- Performance: `python3 test_windows/bench_build.py ./vmake --json` measures vmake's fixed and incremental build overhead (void target, CMake stage variants, native cold/no-op, optional large objects). `docs/WINDOWS_VALIDATION.md` records the method and the current Linux numbers; Windows numbers require a Windows host.

## Execution boundaries

- Targets execute serially in target dependency order. Only source compilation within the active target is parallel. `-j0` resolves to CPU count once; Make/CMake helpers share the same ceiling.
- Required Void build callbacks execute once per invocation, including synchronous subgraphs. VMake does not skip arbitrary callbacks across invocations; Make/CMake own their incremental checks.
- Installation reuses the invocation's BuildCtxs. Do not replay OnBuild during installation. Synchronous subgraph roots are skipped when collecting OnInstall items.
- `cmd/vmake/main.go` initializes Git userland before plugin loading and Cobra execution. Built-in `ext` and `cache` commands skip plugin execution so broken extensions remain removable/updatable and cache maintenance still works.
- `cmd/vmake/tree.go:run(argv, stdout, stderr, env)` is the command seam. `Execute()` is its only adapter to `os.Args`/`os.Stdout`/`os.Stderr`; every invocation resets process-scoped state, unwraps the previous argument validators, rebuilds the Cobra tree through `installCommands()` (recursive `ResetFlags`/`ResetCommands`, then re-registering every built-in command), and returns the exit code as an `int`. Fatal paths panic `*exitError` and are recovered at that boundary so deferred cleanup runs: do not call `os.Exit` outside `Execute()` and do not register a command outside `installCommands()`. Command tests drive that seam in-process through `runCLI`; the only sanctioned spawns of a real `vmake` process are `runSubprocess` (runs to completion) and `newSubprocess` (spawn so the test can signal it) in `cmd/vmake/cli_test.go`, reserved for the plugin/trust/extension and interrupt tests that need a clean process-scoped toolchain manager.
- `cmd/vmake/project.go:openProject` loads the project, calls `pipeline.Require` then `pipeline.Configure`, applies ephemeral overrides via `pipeline.MutateConfig`, and owns resolver cleanup; `pkg/pipeline/prelude.go:prepareBuild` owns the shared build/inspect preparation (needed, chip, config, global flags). `pkg/pipeline/build_phase.go:RunBuild` owns filtering, source preparation, lockfile writing, patches, Kconfig restoration, OnBuild, and scheduling. Post-build lifecycle operations (`RunInstall`, `ValidateInstallPrefix`, `WriteManifest`/`CheckoutManifestLocals`/`CheckoutManifestLocalEntry`, `CleanPackagesInspection`/`ExecuteCleanHooks`, and `ValidateTestProject`/`RunAllTests`) also live in `pkg/pipeline`; schemaVersion-2 build/test reports (`vmake-build.json`, `vmake-test.json`) and GNU/script diagnostic extraction live in `pkg/buildreport`; standalone read-only package catalog discovery (`pkg search`/`pkg show`) lives in `pkg/catalog`; headless configuration editing and sparse `ConfigFile` mutation live in `pkg/config` (`*config.Editor`, `CommitSnapshot`, `SetOption`/`UnsetOption`, plus the TUI workbench value `config.Workbench`/`config.Preview`) and `pkg/pipeline/config_mutate.go` (`MutateConfig`). `pipeline.NewConfigWorkbench` is the single project→workbench projection and `tui.Input` is that value plus the working directory. Keep orchestration in `pkg/pipeline`; compilation/linking/install belong in `pkg/build`.
- `OnRequire` runs first for eager discovery without option values, then again through `FilterDeps` after `OnConfig`/`OnApply`. Direct `Bool`/`String`/`Int` reads fail during discovery; in `FilterDeps`, this package's entry option values and the configured values of its declared global options are readable. Prefer discovery-aware `When`/`If`/`Select` for conditional dependencies. Reachability comes from local roots, not every loaded remote package; see `ComputeNeeded` below.
- `AddRequires` declares package resolution dependencies (pure package IDs only; version constraints live in `vmake.json` `modules`/`sources`); targets declare build edges with `AddDeps` or `UseRequires`.
- `pipeline.ComputeNeeded` (`pkg/pipeline/needed.go`) owns the needed set: active config `Root`/`Roots` overrides root selection when set; otherwise `vmake.json` `"roots"` (or `["//"]` when a root `build.go` exists) wins; BFS follows `Deps` lazily (no directory scanning). Local packages are always identified by canonical path (`"//"` or `"//<rel/path>"`); external containers are `<repo>/<module>` (native, root `build.go` optional) or `<repo>` (registry). `vmake doctor` validates `vmake.json` and flags deprecated `SetRoot()` usage.
- `cmd/vmake/inspect_session.go:openInspection` is the single inspection-command preamble: it takes an explicit root (resolved by `resolveProjectRoot`, no process cache) plus the command session's policy/overrides, enables the read-only script scope and quiet logging (`quiet.ProbeScope`), opens the project, runs `InspectWithOptions(FilterDeps)`, drains blocked writes and closes the resolver. `inspect`, `query`, `query targets`, `check-symbols` and `deps graph|why|check` consume it and keep only output schema, diagnostics text and error mapping; do not copy the preamble into a command.
- `inspect`/`query`/`query targets`/`check-symbols`/`clean` reuse `pipeline.Inspect` (the `clean --all` fallback scans package directories instead); target inspection (`inspect` without `--no-targets`, `query`, `query targets`, `check-symbols`) uses `pipeline.DeclareTargets` for dry-run OnBuild. `inspect --no-targets` skips target declaration entirely; `query targets` lists every needed package with a materialized source tree, including remote packages. `DeclareTargets` intentionally omits `applyBuildContextConfig` to avoid duplicate defines; a nil toolchain preserves existing wiring. `InspectWithOptions(... FilterDeps: true)` runs `FilterDeps` before inspection so these commands see the same package set as `RunBuild`; plain `Inspect` keeps the eager graph. `query config` bypasses `Inspect` entirely. Rendering facts come from the model: `attachInspectionGraph` in `inspect_cmd.go` is the shared graph attach, `query`/`query targets` read `Inspection` accessors instead of re-reading the encoded document, `PackageFacts.Deps` keeps resolver declaration order (the tree prints it) while the encoder sorts the JSON `deps`, and `Inspection.PackageDeps` is the graph-derived edge list. `check-symbols` also enables facts and attaches the graph, then filters `Inspection.Targets`; `TargetFacts` carries `Output` (file name), `OutputPath` (staged path) and `InstallPath` from one `build.PlacementFor` call, so no command re-derives placement.
- Inspection never materializes sources: an absent local SetGit tree declares an empty `BuildDir()`, while present packages receive their resolved `BuildDir()` and `inspect`/`query` enable read-only `scriptfs`. Prefer declarative `WriteBuildFile`/`GenerateFile`/`Generate` and `BuildPath` in `OnBuild` (they defer writes to scheduler execution and emit `$builddir/...` when `BuildDir()` is empty); any procedural OnBuild file writes must guard on `p.DryRun()` (and `p.BuildDir() == ""` for reads/paths) and cannot assume the `src` link resolves.
- `build.PackageLayout` and `layoutFor` in `pkg/pipeline/layout.go` are the single source of truth for per-package build/install dirs and build keys; do not recompute them in callers. `pipeline.LayoutFacts` (`Version`/`Commit`/`PatchHash`/`SourceLink`/`FlagsHash`) is the whole key material: the build stage derives it from live source state and the inspection from the lock, and both must agree for the same package. `PackageLayout.PkgInfo()` is the only layout→`PkgInfo` conversion (a not-ready layout yields no build directory or key). `pipeline.PackageSource`/`packageSources` is the single derivation of a package's source location; `packageSourceDirs` (package roots) and `workspacePackageDirs` (linked/materialized trees) are projections of it. Keys cover toolchain identity, mode, options, global flags and the materialized source commit; remote keys also include source version and patch hash. Buildscript text is action-level: its commands, includes, defines and file lists are captured by action signatures, so a comment-only script edit does not rotate `BuildDir`. Gen rules record the declared input in the generated header's first line (a hashed marker); other files a script writes into `BuildDir()` outside declared actions are untracked and must not be guarded by bare existence checks. A local SetGit patch-only change restores its tree but does not rotate its `BuildDir`; hash any new output-affecting input.
- Incremental actions are described once by `build.plannedAction` and executed by `runPlannedAction`; compile/link/incremental-void producers must not re-derive commands or copy the check/run/save protocol. The action signature covers Kind/Target/WorkDir/TargetOS/Tools/Environment/Commands and declared inputs/outputs; discovered compile dependencies are recorded as file state, not signature material. Recorded inputs are content-addressed except build products (`plannedAction.StatInputs`: link objects, dependency artifacts, prebuilt sources under the package build/install dirs) and outputs, which compare size/mtime/mode only. `Compiler.planCompile` is the only compile command derivation, and `compile_commands.json` uses the same plan's display command. Post-link commands are resolved once into the plan. `actionRecordVersion` is 4.
- Version/commit/lock precedence is owned by `resolver.LockQuery` (`PinFor`/`IgnoredFor`/`LockEntry`/`Decide`): target pins suppress the lock, float suppresses config pins and the lock, then config pin, then lock, then the native-selected value. Do not re-encode this order in resolver/pipeline callers. The desired lockfile is projected by `pipeline.lockDecisions`/`projectLock`; `--locked` compares that projection. Version-table selection (`repo.SelectNativeVersion`, `Pkg.SelectVersionMulti`) stays with the caller.
- `pipeline.ActivatePackage` is the single package-activation path: `DeclareTargets` is its declarative wrapper (dry-run stubs, no config defines), `executeOnePackage` uses build mode with a `Configure` callback for the real config lookup/dependency callbacks. Do not repeat the SetDirs/SetOptions/SetCfgVals/SetToolchain/SetPlatform/SetPackage/ExecBuildFuncs sequence. Declarative callers must run inside a `scriptfs` read-only scope and report blocked writes (check-symbols does).
- `pipeline.ComputeNeeded` is the single build-needed computation (roots + BFS); `RootsFromEdges` is the single reported deps/inspect root computation over package/target edges. Do not reimplement root selection in commands or in `depgraph`. `test` preflight uses `ComputeNeeded`.
- Global flags are explicit: `toolchain.Manager.ToolchainGlobalFlags()` exposes only toolchain/extension globals; `pipeline.aggregateGlobalFlags` merges project flags/defines and `build.HashGlobalFlags([4][]string)` hashes the explicit value. Never reintroduce a project-flag scratchpad on the manager.
- `pkg/tui/layout.go:Model.layout` is the single screen owner: it derives panel geometry, visible rows, hitboxes and dialog rects purely from model state, and `View()` returns `layout().view`. Input handlers consume the same value; do not reintroduce render-written geometry fields on `Model`. The option/choice/detail viewport anchors (`optOff`/`choiceOff`/`detailOff`) are navigation state written by `Update`'s `syncScroll`, never by layout or rendering.
- Effective configuration values have one implementation in `pkg/pipeline`: `PackageConfigValues` is the build projection, `DisplayPackageValues` the declared-option projection carried on the inspection's package view (`PackageView.Values`/`PackageView.Platform`), `collectAllPkgOptions` the build-key projection, `applyGlobalValues` the OnApply projection (resolved mode/toolchain/target defaults) and `ProjectGlobalValues` the project-global projection. Command renderers consume these; do not re-derive effective values in `cmd/vmake`.
- `repo.SourceManager.WouldMaterialize` and `SourceResult.Materialized` share one reuse predicate with `EnsureSource`; the source-phase banner must call `WouldMaterialize`, not a copied predicate. The request value itself is projected once by `pipeline.sourceRequestFor` for local SetGit packages and own-Git members (banner and `EnsureSource` consume the same value); the remote loop builds one `SourceRequest` for both banner and fetch. Resolver probes and manifest restore keep their explicit reduced requests (`ResolveOnly`, ref-only).
- `pipeline.packageLocation` is the single derivation of `OwnerTreeRoot`/`PackageRoot`/`SourceTree`/`ThirdPartyRoot`/`TreeRoot`; do not recompute `<deps>/<owner>/src[/<member>]`, `third_party`, or local `src` links in callers. Keep the package-root vs actual-source-tree distinction explicit (`SourceDir()` vs `SrcDir()`).
- Header/boundary audit runs on `build.headerAuditor` over an explicit `auditEnv`; `CheckExistingBuildBoundaries` must not construct a partial `Scheduler`. `Scheduler.auditorFor` lazily supplies the same environment for direct Scheduler construction in tests. Header path canonicalization goes through `pathCanonCache.realPath`, which resolves each path once per build; do not call `filepath.EvalSymlinks` per dependency header. The header-file inclusion rules (undeclared, private, transitive) have one emitter pair in `header_check.go` (`headerInclusionError`/`transitiveInclusionError`); the declared-path directory variants in `checkTargetDeclaredPaths` stay inline. The depfile and static-source paths only discover includes, so a new discovery path must reuse those emitters instead of writing the messages again.
- `build.PlacementFor` (used by `Scheduler.placementFor`) is the single artifact placement value (source output, PE import library, per-package staging dirs, install subdir/name, post-link outputs). A successful target from a session-bound scheduler is recorded once as a `targetOutcome` (result and placement) in the shared build `Session`; `BuildResult.Targets`/`TargetPlacements` read that record, keyed by full target name and containing successful targets only, so additional schedulers and synchronous subgraphs do not need a separate placement merge. `TargetPlacements` exposes non-void targets only. `publishTarget` and `ArtifactInstaller` (via `PkgInstallInfo.Placements`) consume the placement; a target without a placement was not produced by this build and is not installed, so `PkgInstallInfo` must carry `PlacementFor` results rather than being hand-built.
- `build.ParseDependencyRef` (exported form of `parseDependencyRef`) is the single parser for target dependency strings (bare target, `pkg:target`, `pkg/sub:target`, `pkg:*`); graph, subgraph, `pkg/pipeline` edge projection and command callers must use it instead of re-splitting on `:`/`/`. `build.NewBuildGraph` (strict) and `build.AuditBuildGraph` (infallible audit mode used by `pipeline.BuildUnifiedGraph` and `CheckProjectDeps`) share the single target/package dependency expansion engine in `pkg/build/graph.go`: `resolveDepSpec`/`classifyDep`, `declaredTargetDeps` (`UseRequires` expansion), `visibilityPathFor`/`checkInternalVisibility`, and `packageCycleError` (DD-22, DD-36). They keep distinct traversals on purpose: strict validates declared edges (raw target deps, `OnRequire` meta deps, subgraphs) and returns the first error, while audit reports expanded package/target edges and collects issues, including `Unmaterialized` tolerance. Their error contracts are not reducible: strict fails on the first resolution error (`dependency not found: <dep>`, `circular dependency detected`), while audit reports `dependency not found: <dep> (from <target>)` or `(resolved: <target>)` and can report an extra package cycle when a target is missing. `TestStrictAndAuditAgreeOnNodes` pins the node-data equivalence (targets, deps, order) that any future merge can build on; do not merge the traversals without re-deriving both error contracts.
- `cmd/vmake/session.go:commandSession` owns `--set`/`--locked`/`--offline`/`--config` and the storage lifecycle; `openProject` must consume the session instead of reading those package globals. `BuildOptions` has no `Locked/Offline`; `ResolveParams.IgnoreLock` is translated to `LockPolicy.IgnoreAll` in `NewContext`, and the source stage derives `locked/offline` from `effectiveLockPolicy()`.
- Phase outputs are explicit and have no mirrored copies: `Require` sets `Resolver`/`DepGraph` directly, `prepareBuild` returns its `buildPrelude`, and `applyConfiguration` copies the Configure result's fields onto the context. `RuntimeContext.Configuration()` is a derived-on-read view: it clones container maps and flag slices on each call (`*api.Option`/`*api.KConfigEntry` definitions stay shared read-only), so mutating a field is visible immediately and no snapshot has to be refreshed. `Configure` runs on a shallow context copy and commits only on success. Do not add a second stored copy of phase state; add a view or return the value.
- Environment variables that affect compiler, linker, or CMake output must be added to `internal/envsig`. Action signatures and CMake configure fingerprints hash only that allowlist; `VMAKE_ENV_EXTRA` is an escape hatch for unusual toolchains, not the place for built-in variables.
- Local and remote packages share scheduling, compilation, and linking. Keep source materialization, directory selection, and patch handling at their existing boundaries.
- Remote buildscripts and extension code are gated by `~/.vmake/trust.json` records keyed `kind:name`; trust is bound to the repository identity (registry origin URL, native URL template, or extension origin URL), not to a commit or worktree state. Updates keep trust; only remove/untrust revoke it. Loading holds the shared `~/.vmake/_locks/{repo,ext}_<hash>.lock`; extension locks stay held until the process exits so build-time toolchain installs read the trusted worktree. `flock` is not reentrant, so trust decisions must not call a command that takes the exclusive lock on the same repository.

## Interpreted scripts and generated symbols

- Buildscripts and plugins are reinterpreted each invocation: no `.so`, `-buildmode=plugin`, or module generation. Their usable binary imports are registered in `pkg/buildscript/yaegi_loader.go` and `pkg/plugin/loader.go`.
- Script-facing package-level exports in `pkg/api` are an explicit allowlist in `pkg/api/yaegi_symbols.go`; add new symbols deliberately rather than exporting every Go API. `TestYaegiSymbolsComplete` checks exported symbols are registered there; native runtime binding and target snapshots are explicitly excluded and must remain unavailable to scripts. `pkg/toolchain` and `pkg/plugin` maintain their own symbol tables.
- The script *method* surface is explicit in `pkg/api/script_methods.go`: `scriptMethodAllowlist` holds the documented or script-used methods and `scriptMethodPending` the visible-but-host-only/undocumented residue (currently empty after DD-27 phase 2). Host wiring lives on exported `api.Bind*` functions in `pkg/api/bind.go`, which are host-only and excluded from `YaegiSymbols` by the `Bind` prefix rule in `TestYaegiSymbolsComplete`; do not call unexported host methods or fields from other packages. `TestScriptMethodManifestMatchesVisibleSurface` fails when a method on a registered type is added or removed without classifying it, and `TestScriptTypesDoNotPromoteExportedFields` fails if a context/Package regains an exported data field. DD-27 phases 1–3 are landed: `ConfigAccessor` and `PackageMeta` fields are unexported and reached through `Bind*` accessors, and `TargetRegistry`/`InstallItemHolder` promote only allowlisted methods.
- Cobra/pflag bindings under `internal/yaegisym` are generated. After Cobra/pflag upgrades, run `go generate ./internal/yaegisym/` with `yaegi` (from `github.com/traefik/yaegi/cmd/yaegi`) on PATH, matching the version in `go.mod`; do not hand-edit generated bindings.
- `internal/gosrc.ListGoFiles` selects Go files using the running host's GOOS/GOARCH with CGO disabled, independently of the C/C++ target. It excludes `_test.go` and files importing `C`; the loaders merge selected files for interpretation.
- Pass `[]string` directly to `AddCFlags`, `AddDefines`, etc.; spreading it with `...` into their `...any` parameters fails under yaegi. The API flattens slices itself.
- Custom `GlobalOption`s are auto-exported to every package as `CONFIG_<NAME>` defines (choice values add `CONFIG_<NAME>_<UPPER_VALUE>`); plain package options become macros only through `GenerateConfigDefines`/`GenerateConfigHeader`. Options may only be declared during `OnConfig`.
- `internal/scriptfs` wraps common `os` operations, `filepath.Walk/WalkDir`, and `exec.Command` so relative paths resolve against `pkg.SourceDir()` when set, otherwise the build.go directory (plugins resolve against their entry directory). `os.Chdir` is rejected. `OnBuild`/`OnInstall`/`OnClean` callbacks run inside `os.Chdir(SourceDir)`, so unwrapped APIs such as `exec.CommandContext` and `template.ParseFiles` resolve relative paths there. `OnConfig` runs before source binding inside the loaded build.go directory (the registry wrapper checkout for registry packages); `OnRequire`/`OnPackage` and a later `TargetVoid` `SetBuildFunc` use the process cwd. Supply explicit absolute paths/command directories.

## Directories and incremental behavior

- `SourceDir()` is the package root; `SrcDir()` is the actual source tree and can differ after `SetGit`; `BuildDir()` is build-key-specific. `p.Run` and `p.Make` use BuildDir. For an in-source Makefile use `p.Make("-C", filepath.ToSlash(srcDir), ...)`; the source directory must be absolute. Make/CMake helpers inherit the invocation jobs ceiling.
- Prefer `CMakeConfigure`/`CMakeBuild`/`CMakeInstall`. Use their directory/configuration setters and `CMakeBuildDir()`/`CMakeInstallDir()` getters; defaults are `BuildDir()/cmake` and remote InstallDir or local `BuildDir()/staging`. Keep CMake artifacts separate from `SetPrebuilt` symlink destinations.
- `CMakeConfigure` fingerprints its inputs in `<CMakeBuildDir>/.vmake_configure.json` and skips unchanged runs; new files matched only by `file(GLOB)` do not invalidate it—use `CONFIGURE_DEPENDS` or clean the build tree.
- Third-party sources materialize as a single shallow working tree per package at `<project>/.vmake_deps/<repo>/<owner>/src[/<member>]` (local SetGit packages: `.vmake_deps/local/<pkg>/src`, linked from `<pkgDir>/src`). The selected commit's objects are fetched once into the shared content-addressed cache `~/.vmake/cache/git/<urlhash>.git` (one bare repo per upstream URL, anchored under `refs/vmake/<commit>`; `VMAKE_CACHE` overrides the default cache root and `VMAKE_GIT_CACHE=off` disables the cache and fetches depth-1 directly from the package's upstream URL), and a lock-pinned working tree at a cached commit is then fetched depth-1 from that cache without touching upstream; ref resolution (`git ls-remote`), HEAD materialization, cache misses, and the full-clone fallback for servers that reject SHA fetches still contact upstream. Same-commit work (patch-set changes) is restored in place with `checkout --force --detach`/`clean -fdx`; a different commit recreates the tree. Builds hold the exclusive project lock, and each tree is serialized by `tree_<hash>.lock` while each cache namespace is serialized by `cache_<urlhash[:16]>.lock`. Keep `_locks` outside guarded package directories and never unlink held lock files. `clean`/`clean --all` keep these working trees, and `distclean` keeps them unless `--purge-sources` is passed; ordinary cleaning does not reset source edits.
- Storage layout diagrams are living documentation: whenever paths, lock/state files, or cleanup semantics under `~/.vmake/`, `.vmake/`, or `.vmake_deps/` change, update the structure diagrams in `docs/VMAKE_HOME.md` and every other doc or bundled skill file that states those paths (for example `docs/ARCHITECTURE.md`, `docs/FIRMWARE_BUILD_DESIGN.md`, `cmd/vmake/skills/vmake/`) in the same change; do not leave stale paths.
- `.vmake/vmake.lock` uses schema `version: 2` (`containers` for external module containers and `sources` for independent `SetGit` packages, including registry packages, local `SetGit`, and native `SetGit` members); `vmake deps sync|update|prune|pin|unpin` manage the lockfile and `.vmake/project.json` pins (`--locked` / `--offline` enforce locked/cached builds). Default builds, `deps sync`, and `deps update` retain lock entries belonging to inactive SKU configurations (and `--locked` tolerates them); only explicit `vmake deps prune` or `--prune` drops inactive entries. Preserve offline locked resolution rather than adding unconditional fetches.
- `.vmake/local.json` stores machine-local state (never tracked in git): the developer's active configuration cursor (`config`, set by `vmake config use`) and local package source links (`links`, set by `vmake pkg link`). Linking supports native containers (`<repo>/<module>`), registry packages (`<repo>/<pkg>`), native `SetGit` members (`<repo>/<module>/<path>`), and local `SetGit` packages (`//<path>`), removing that target's existing `.vmake_deps/.../src` and `state.json` while keeping `out/` and own-Git `third_party/` sources. Linked targets skip materialization/version/tag/constraint checks and keep outputs under `.vmake_deps`; the lock entry is preserved but ignored. Native container links supply `vmake.json`, member `build.go`s, and options from the link tree; registry and `SetGit` source links keep the wrapper `build.go` and replace only the upstream source. Native own-Git member third-party sources go to `.vmake_deps/<owner>/third_party/<member>`.
- Tracked build configurations live under `configs/**/*.json` (default `configs/default.json`), storing sparse explicit overrides (keyed by canonical package ID) plus optional `description` and `root`/`roots`. CLI `--set`/`--unset` and cross-package option reads use `<pkg>:<opt>` syntax. `.vmake/project.json` stores only team-shared `default_config` and dependency `pins`; a present `local.json` `config`, `project.json` `default_config`, or CLI `-c/--config` selector that is missing/invalid must error rather than fall back. All config files share `.vmake/vmake.lock` and `.vmake/project.json` pins; `config list|use|copy|describe` do not run Require/Configure, whereas `config check [--all]` strictly validates options, reachability, and dry-run target declaration.
- Kconfig presets are make target names, not complete `.config` files. Generation belongs in `EnsureConfig`/TUI `ensureConfigCmd`; `restoreKConfigFiles` only restores saved content. Preserve unchanged config mtimes so incremental stamps remain valid.
- Custom post-link inputs/outputs require `AddPostLinkDeps`/`AddPostLinkOutputs`. Missing outputs or changed inputs trigger relinking and all post-link steps; command arguments do not imply outputs. Hex/Bin/Strip helpers declare their outputs automatically.
- `autoconf.h` is package-local; public headers must not include it. Cross-package config propagation uses exported/imported options and generated defines. `SetDefaultVisibilityHidden` is also package-local, not a dependency-wide policy.
- Module containers and build packages are decoupled per `docs/adr/0001-separate-module-containers-from-packages.md`, and container encapsulation follows `docs/adr/0002-container-encapsulation.md`: containers (`vmake.json` `modules`, string constraint or `{"version"}`/`{"path"}`) own git checkouts and semver resolution (with diamond constraint intersection) and may declare self-contained `"repos"`, `"dev_roots"` (local-only fallback roots), and 1-to-1 `"exports"` whitelists (`Graph.CanonicalPackageRef` guarantees single `PackageNode.ID` identity across internal/external refs); third-party `SetGit` sources always clone from their configured Git URLs; package options marked `SetInternal(true)` are enforced across container seams in config/CLI/TUI/`OnConfigureDeps`/cross-package reads/`ImportConfig`. Consult ADR-0001, ADR-0002, and `GLOSSARY.md` before changing container/package resolution.

## Cross-platform constraints

- Artifact names and linker/CMake behavior follow the project's `target_os`, not the host. Bare-metal uses `none`; the compiler triple is the project option `target_triple` / `Package.TargetTriple()`. Toolchain manifests may declare `target_os`/`target_triple` defaults that apply only while the project leaves them unset; `default_flags` stays rejected there. They use host-keyed `installations` with explicit `root_dir`; legacy `host`/`install` fields are rejected too.
- Configured tools resolve strictly: installation-relative tools stay under that installation's `bin`, with no PATH fallback. Preserve definition errors rather than selecting the host toolchain. Unset MAKE is resolved only when make is needed; explicitly configured MAKE is validated.
- Route git invocations through `internal/gitcmd.Args` to preserve LF content, long paths, and symlink settings. Use `filepath.ToSlash` for path arguments sent to MSYS `sh`/`make`/`tar`/`curl`; native `cmd.Dir` retains OS separators.
- Windows storage requires real symlinks (Developer Mode or elevation); do not substitute junctions. Git for Windows supplies Unix userland, not a C compiler or make. Diagnose a fixture with `../../vmake.exe doctor --toolchain NAME` from its project directory.
- Windows GNU compile/link/archive commands reference content-addressed response files under the package build dir (`state/rsp`): compiles share one file per target options set across translation units and builds, links/archives keep their whole argv there, and temporary per-command response files must not return; `compile_commands.json` must retain expanded arguments. VMake-built PE shared libraries link through `.dll.a` import libraries; never whole-archive these. ELF-only symbol policies must fail on PE targets.
- macOS hosts use the builtin `cc`/`c++` toolchain with no `objcopy`/`objdump`; do not require them there. Native links are Mach-O: dependency archives use `-force_load` (no GNU group/whole-archive), `TargetShared` links with `-dynamiclib` and an `@rpath/<name>` install name, binary consumers get `-rpath` entries for the dependency directories plus `@loader_path`/`@loader_path/../lib`, shared-library consumers get the dependency directories plus `@loader_path` only, and ELF-only symbol policies must fail on Mach-O targets. Only `target_os=darwin` selects this path; values are not aliased. Mach-O artifacts are out of scope for `vmake check-symbols`.
- Apple ships GNU Make 3.81; Kconfig/kernel/U-Boot builds need 3.82+ (`brew install make`, then point the toolchain's MAKE at `gmake`).
- `vmake test` executes native test binaries. Cross/bare-metal targets use `vmake build --tests`; test targets are excluded from ordinary builds and installation.

## Repository conventions

- Do not add comments unless explicitly requested. Use function-type callbacks and composition instead of introducing interfaces.
- API mutators are fluent: `SetX` sets a single value, `AddX` appends, `RemoveX` removes. Keep fields private where the surrounding API uses accessors.
- Imports are grouped stdlib → external → local. Logging uses `vlog "github.com/spock2300/vmake/pkg/log"`; available methods are Debug/Info/Error/Fatal, not Warn.
- `cmd/vmake/skills/vmake/` is embedded, test-checked user documentation. After CLI changes regenerate `references/cli.md` with `CGO_ENABLED=0 go test ./cmd/vmake -run '^TestSkillCLISnapshot$' -update-skill-ref`; keep the API/storage references in sync with code.
- API misuse raises `*BuildScriptError` through `fatalScript` (`pkg/api/errors.go`), recovered by script execution boundaries. New API validation must use that path rather than exiting with `vlog.Fatal`. Ordinary library errors are returned to callers.
- Preserve strict contracts: fix invalid callers rather than adding fallback chains or silent defaults. IDE plugins, GUI, and distributed builds are permanent non-goals; MSVC is deferred. See `docs/GOALS.md`.
- Within 1.x, do not remove script-facing API symbols, documented methods, or CLI flags, and do not change their semantics; add new ones instead. Removals happen only at 2.0. This is an internal rule (DD-34), not a public compatibility promise.

Detailed references: `docs/GOALS.md` for the long-term goal, acceptance definition, milestones, and non-goals; `docs/ARCHITECTURE.md` for execution flow, `docs/BUILD_SCRIPT_API.md` for script contracts, `docs/BUILD_RESULT.md` for build/test reports, `docs/INSPECT.md` for the `vmake inspect` JSON schema, `docs/VMAKE_HOME.md` for storage layout, `docs/EXTENSION_PLUGIN.md` for plugins/toolchains, and `docs/DESIGN_DECISIONS.md` for intentional resolver limitations.

## Coding Guidelines

**Think before coding.** State assumptions explicitly. If multiple interpretations exist, present them. If a simpler approach exists, say so.

**Minimum code that solves the problem.** No speculative features, abstractions, or configurability. If 200 lines could be 50, rewrite it.

**Surgical changes.** Touch only what the task requires. Match existing style. Remove imports/variables made unused by your changes — don't touch pre-existing dead code.

**Goal-driven execution.** Convert tasks into verifiable outcomes: "Add validation" → "write tests, then make them pass". For multi-step tasks, state a plan with verify checks.
