# Structured build results

`vmake build` (including bare `vmake`, `build -iV`) and `vmake rebuild` atomically publish `build/vmake-build.json`; `vmake test` publishes its own `build/vmake-test.json`. The two documents use the same schemaVersion 2 shape but are written by separate invocations: a test run never rewrites the build report, so the last successful build state survives passing, failing, no-test and preflight-failed test runs. These files are separate from the dependency version manifest in the install directory. Build scripts do not declare hardware or IDE configuration.

The version 2 JSON object contains all version 1 fields plus `durationMs`, `diagnostics`, `command`, `tests`, report provenance (`vmakeVersion`/`vmakeCommit`), and (when results were collected) `summary`, and `error` is now a concise one-line summary:

| Field | Meaning |
| --- | --- |
| schemaVersion, buildId, root | Schema version (2), unique invocation ID, absolute project root |
| status | running, succeeded, failed, or cancelled. For `vmake test`, succeeded means every executed test target passed and also covers a host project with no test targets; failed means at least one test failed or the test platform check/build failed |
| command | `build` for a build, `rebuild` for `vmake rebuild`, and `test` for `vmake test`; a missing value means `build` in reports written before this field existed |
| started, finished, durationMs | UTC timestamps and wall-clock duration in milliseconds; durationMs is 0 while running |
| error | One-line failure summary, at most ~300 characters and never the full command line. It is the first parsed diagnostic formatted `file:line[:column]: message`, or the compacted error text when no diagnostic was parsed. Empty on success |
| diagnostics | Always an array, never null. On success it is an empty array; on failure it holds the parsed error diagnostics. Each entry has `severity` (error), `code` (`VMAKE_E_COMPILE`, `VMAKE_E_LINK`, `VMAKE_E_BUILD`, `VMAKE_E_SCRIPT`, or `VMAKE_E_TEST`), `message`, and optional `file`, `line`, `column`, `package`, `target`. A `vmake test` failure without a build diagnostic (a failed test or a platform preflight refusal) gets exactly one `VMAKE_E_TEST` error entry carrying the same concise message as `error`; per-test details stay in `tests[]`. Error output is parsed from the standard GNU `file:line[:column]: severity: message` form, and GNU ld's `file:line: undefined reference to ...` / `file:line: multiple definition of ...` lines (with an optional `(section+offset)` annotation before the message) are parsed as located errors; all are attributed to the failing target and stage. Unparseable command failures produce one fallback diagnostic whose message prefers the last undefined-reference/multiple-definition line, then the last `error:` line, and only then the raw output tail. `VMAKE_E_SCRIPT` entries come from build script/API errors and carry the package name. Recovered script panics do not dump the interpreter's raw `N:M: panic: main...` frame; only the concise BuildScriptError message and report diagnostics remain |
| summary | Present whenever results were collected: on success for build/rebuild, on a failed build or test whose scheduler produced a partial result, and for `vmake test` after the build phase so test counts remain readable. It is omitted when the failure happened before any target was scheduled (for example a buildscript error or platform preflight refusal). `durationMs` repeats the top-level duration; `targetsTotal`, `targetsBuilt`, `targetsUpToDate`, `targetsFailed`; `testsFound` counts discovered test targets, while `testsPassed` and `testsFailed` count executed entries; all three are always present (zero for build/rebuild); `filesCompiled`, `filesLinked` and `actionsUpToDate` count compile and link actions only (post-link steps, void build callbacks and installation are not actions); `artifactsInstalled` equals the artifact count; `callbacks` counts executed `void` targets whose `status` is `built` (their callbacks always run); `externalStages` counts CMake and Make helper stages executed by this invocation (`CMakeConfigure` when it configures rather than reuses its fingerprint, `CMakeBuild`, `CMakeInstall`, and `p.Make`; dry-run calls and cached configures do not count); on a succeeded report `noOp` is true exactly when `filesCompiled == 0`, `filesLinked == 0`, `changedFiles` is empty and `externalStages == 0`, so a no-op may still have run callbacks and installed artifacts; `changedFiles` is the sorted, unique list of compiled files recorded as `package:relative/path` with slash separators (`[]` when nothing was compiled; an entry that is already absolute or package-qualified is kept as-is without a second prefix). On a partial failure the counts describe the work attempted before the failure, `targetsFailed` is the number of distinct failed target names in the diagnostics (or 1 when a target failure is known without a name), and `artifactsInstalled` is 0. A failed report never carries `noOp: true`: when a failure would otherwise look like no work (for example a failed `void` callback or CMake configure error before any compilation), `noOp` is recorded as false, even when `targetsFailed` stays 0 because no target name is known. Counts describe the scheduler work of this invocation, so a no-op build has zero compiled/linked files and a one-file incremental build has one of each |
| configFile, configSha256 | Selected `.vmake` filename and SHA-256 of the exact bytes used to resolve configuration; SHA of empty bytes for the unsaved default |
| global, packages | Effective global values, and per-package values for the packages that participated in this build (needed packages, including subgraphs). `global` is populated as soon as configuration is resolved, so a failed report still identifies the attempted configuration. With `--install`, the separate install manifest also lists every local package in the dependency graph, even if it was not built; its remote entries are limited to installed packages |
| toolchain, mode | Effective main build toolchain and mode; package overrides remain in packages |
| vmakeVersion, vmakeCommit | Version string and abbreviated VCS commit embedded in the running vmake binary (`dev`/`unknown` when built without module version or VCS metadata). They are captured when the running report is first written and kept unchanged by finish and partial updates, so a report identifies the binary that produced it |
| compileDatabase | Absolute path to the compilation database, or empty if none was generated. It is recorded whenever the file exists, including on a failed build |
| targets | Executed default targets: package, target, kind, publishable output paths (including declared post-link outputs), `status`, and `durationMs`. On a failed build the array keeps the targets that completed before the failure; the failing target is identified by `diagnostics[].target` and counted by `summary.targetsFailed`. A failure outside target execution (for example a package-level `OnBuild` CMake configure failure) is package-scoped: no target callback ran, so `diagnostics[].target` stays empty and `targets[]` may stay empty; vmake does not invent a target attribution for it. `status` is `built` when the target compiled or linked anything in this invocation, or when it is a `void` target; otherwise `up-to-date`. A `built` `void` target means its callback ran, not that any file was produced. `durationMs` is the target wall time (0 when too fast to measure) and is nonnegative. Non-default targets are never executed, even when another target depends on them, so they are never recorded; default targets built through a subgraph are recorded, but installation walks the main graph and skips subgraph roots, so they normally do not add artifacts. Test targets appear only for `vmake build --tests` and `vmake test` |
| tests | Always an array. Empty for build/rebuild, for a `vmake test` whose build phase failed, and when no test targets were discovered; otherwise one entry per executed test target. Each entry has `name` (`package:target`), `package`, `target`, `passed`, `elapsedMs`, `exitCode` (0 on success, the process exit code on failure, -1 when a signal terminated it, 1 when the code is unavailable), `signal` (omitted unless a signal terminated the process; platform wording such as `segmentation fault` or `killed`) and `output` (the combined stdout/stderr tail captured for that test, bounded to 4096 bytes; when longer it starts with `...[truncated]`). Test entries never contain vmake's own `PASS`/`FAIL` progress lines |
| artifacts | Only files actually installed by this invocation, each with package, target, buildPath, installPath, size, sha256. PE shared targets also record their `.dll.a` import library |

`targetsBuilt` counts target records with status `built`, including `void` targets whose callbacks always run; `noOp` can be true while `targetsBuilt` is nonzero and `externalStages` is zero (for example eight callback targets).

On success `vmake build`/`vmake rebuild` prints one summary line to stdout. The normal form is `Build succeeded: 34 targets (9 built, 25 up to date), 1 callbacks, 1 compiled, 1 linked, 7 installed in 4.9s (buildId=...)`, with the `N callbacks` part present only when at least one `void` target callback ran and the `N external stages` part present only when CMake/Make helper stages ran. When nothing was compiled or linked and no helper stage ran the line reads `Build succeeded: no compilation (34 targets, 26 up to date, 8 callbacks, 7 installed) in 5.0s (buildId=...)`, which makes a true no-op unambiguous. A CMake-only build with no targets instead prints `Build succeeded: 0 targets (0 built, 0 up to date), 0 compiled, 0 linked, 0 installed, 2 external stages in ...`; `externalStages` is nonzero and `noOp` is false, and no target is invented for the external work. The summary is the only success line: the pipeline no longer prints a separate `Build succeeded!` line, so a successful run ends with exactly one summary (`vmake build --install` still prints `Install succeeded!` after the build phase). On failure the same command prints one `Build failed: <error>` line to stdout while the concise `Error:` line and the raw tool diagnostics remain on stderr. With `-q`, buildscript `fmt.Printf`/`print` output is suppressed so the summary line is the only stdout; stderr is unchanged (compiler warnings and errors still stream). The `filesCompiled`/`filesLinked` counts intentionally exclude post-link, `void` callback and installation actions; callbacks are counted separately and `targets[]` carries per-target status.

`vmake test` writes the same schema with `command:"test"` to `build/vmake-test.json`; it never rewrites `build/vmake-build.json`. The running test record replaces any previous test report before configuration work, and a completed test report carries the build targets, summary, `tests[]` and compilation database from its own build phase when that phase ran. A later failing test run overwrites an earlier succeeded test report with a new buildId, while the build report keeps the previous build's identity. Before building, the platform preflight refuses a project whose effective root platform cannot run native tests (`target_os` is `none`, differs from the host, or `target_triple` is non-empty): it writes a failed test report with the `cannot run tests for project target ... use 'vmake build --tests'` error, preserves the build report, and does not create build-key directories or the compilation database. Host projects with no runnable test target succeed with `summary.testsFound: 0`, `status: "succeeded"`, and exit 0 with a `Tests succeeded: no test targets` summary. `vmake build --tests` is still a build: zero test targets is not an error there and its test counts stay zero. Test reports keep `summary` on test failure because the build phase completed; when the build phase itself fails, the failed report keeps the completed targets and partial summary collected before the failure, still carries the resolved configuration identity, packages and compilation database, and records no test entries (no tests are run after a failed build phase). `summary` is omitted only when the failure prevented any target from being scheduled, such as a buildscript error or the platform preflight refusal. `vmake test` never installs outputs, so `artifacts` is empty. It prints `Tests succeeded: <passed>/<found> passed in <duration> (buildId=...)` on success, `Tests succeeded: no test targets (buildId=...)` when none were declared, and `Tests failed: <error>` on failure; with `-q` that is the only stdout. The report is the single overall test summary: per-test `PASS`/`FAIL` lines still print, but there is no separate `N/M test(s) passed` stdout line. Test `PASS`/`FAIL` progress and child output keep streaming as before; the captured `tests[].output`, `tests[].exitCode` and `tests[].signal` are report data only. Test binaries execute with their working directory set to the package's `BuildDir()` (the directory that contains the test executable), so relative paths in a test program resolve there. A signaled test records `exitCode: -1` with the platform signal name in `signal`.

## Console output

The default view keeps progress that carries new information: compile/link/generate/install action lines, buildscript prints, and the final summary. Per-target `[package:target]` headers are detail and print only with `-v`; the report and `changedFiles` carry the package/target context at default. `-v` restores the headers together with the build order and the full captured CMake logs.

`Downloading package sources...` is printed only when at least one needed source actually needs materialization or a remote resolve; a no-op build does not print the heading. CMake helper output is captured instead of streamed raw. `CMakeConfigure` prints one `cmake configure: done` line at default (or `cmake configure (cached): <dir>` when its fingerprint is unchanged), and `CMakeBuild`/`CMakeInstall` print their step or installed/up-to-date counts. CMake's `-- ...` configure scaffolding, Ninja progress and `-- Up-to-date` install lines are hidden from the default view (the captured log stays available with `-v`); Ninja steps and install counts are summarized. CMake warning and error lines, including compiler `file:line: warning:` diagnostics from the build stage, stream to stderr rather than stdout. `-v` additionally prints the full captured CMake log; `-q` prints nothing on stdout for a successful configure (the summary is its only default line) while warnings and errors still reach stderr. A CMake stage running longer than 10 seconds prints `  cmake <stage>: still running (Ns)` to stderr every 10 seconds (including under `-q`), so a captured long build is not silent; fast stages print no heartbeat.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Success, including `--help` and `version` |
| 1 | Operation failure: compile/link/buildscript/test failure, test preflight refusal, report or result-write failure, storage failure |
| 2 | Usage or project-resolution failure: unknown/invalid flag, missing required argument, not inside a vmake project |
| 130 | Interrupted by SIGINT |
| 143 | Interrupted by SIGTERM (non-Windows) |

Ordinary build, script and test failures are never reported as 2.

The full failing command and raw tool output are deliberately no longer stored in the report: the raw compiler/linker diagnostic remains on stderr (streamed exactly once), and the report carries the parsed form plus the concise summary. On failure the final human `Error:` line on stderr is the same concise summary as `error`. A link or other command failure whose output has no parseable location yields one fallback diagnostic with the stage-derived code; its message prefers the last `undefined reference`/`multiple definition` line, then the last `error:` line, and only then the trimmed output tail (up to 1000 characters), and its summary is truncated to the same ~300-character budget. GNU ld's `file:line:(section): undefined reference to ...` and `multiple definition of ...` lines are parsed as located errors, so a link failure summary names the source location and the unresolved symbol instead of a build-key path prefix.

Artifact paths are absolute, and every artifact has a nonempty installPath. An extra `AddInstalls` file may have an empty target. The artifact list comes exclusively from the invocation's installer records: installed main outputs, declared post-link outputs, SDK public includes and extra files are included. vmake does not create a main output file for a `TargetVoid` target, so installation normally returns before installing its declared post-link outputs even though they appear in targets. Directories contribute only files that passed the installer filter in this invocation; stale destination files are excluded. `installPath` is not necessarily under the global prefix: a package's `InstallContext.SetPrefix` redirects its artifacts, and installation only clears the global `--prefix` (default `install/`), not custom prefixes. Source and installed bytes must have matching SHA-256 identities. The build context is reused without a second OnBuild invocation or build-key reconstruction. Incremental no-op builds with installation still publish a fresh build ID and verify installed file identities. Without `--install`, artifacts is an empty array even if a previous installation remains on disk; configuration, targets and the compilation database are still reported.

The main output of an `object` target is an intermediate link input. It is excluded from the target's published outputs, including prebuilt object targets. An object target with no declared post-link outputs therefore has an empty output list. Compilation and linking still use its object file normally. Other executed default targets retain their output paths in targets for build metadata, but uninstalled outputs never become artifacts. Runtime installation skips static-library targets, so their `.a` main output and declared post-link outputs are not installed as target artifacts; `--install-type sdk` includes libraries that are actually installed. Test targets and targets marked `NoInstall` are not installed either. No extension-based display filter is needed by consumers.

A running record replaces the previous success of the same document before configuration/build work starts, under the normal project storage lock: build/rebuild rewrites `build/vmake-build.json` and test rewrites `build/vmake-test.json`. Configuration identity is captured from the same bytes that were parsed, and rechecked after build/install. Success requires build, declared post-link outputs, installation and result collection to complete; `vmake test` additionally requires every executed test to pass, while a host project with no runnable test target succeeds. A project whose effective root platform cannot execute tests fails the platform preflight before the build starts and leaves the build report intact. Failure/cancellation clears artifacts. A build or build-phase failure also publishes the partial result: the completed targets, package values, configuration identity, compilation database and a summary whose counts cover the work attempted before the failure, with `targetsFailed` counting distinct failed target names. That partial summary is omitted when the failure happened before scheduling, and installation is never attempted after a build-phase failure. For `vmake test`, a test failure after the build phase keeps the full build summary so the test counts remain readable. Panic unwinding cannot publish success before collection finishes. Termination before the running record reaches disk, or a failed first write, can leave the preceding report in place; buildId, configSha256 and artifact sha256 identify whether it belongs to the invocation being watched. clean/distclean and `pkg clean` remove both `build/vmake-build.json` and `build/vmake-test.json` before cleanup. `vmake clean` also removes the now-stale `build/compile_commands.json`; when build-key directories for other configurations remain, it prints one note with their count and a suggestion to use `vmake clean --all` or `vmake distclean`, and leaves those directories in place.

Consumers must require status=succeeded, matching project/configuration, and verify selected artifacts against sha256 before executing them. A report proves the outputs of a particular completed build; it does not assert that all source files are unchanged since that build. Keep buildId when correlating tasks, and do not infer freshness from installed directory contents. Reports use schemaVersion 2; the version 1 fields keep their meaning, and consumers pinned to schemaVersion 1 must accept the new version.
