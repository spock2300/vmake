# Structured build results

`vmake build` (including bare `vmake`, `build -iV`) and `vmake rebuild` atomically publish `build/vmake-build.json`. This is separate from the dependency version manifest in the install directory. Build scripts do not declare hardware or IDE configuration.

The version 2 JSON object contains all version 1 fields plus `durationMs`, `diagnostics` and (on success) `summary`, and `error` is now a concise one-line summary:

| Field | Meaning |
| --- | --- |
| schemaVersion, buildId, root | Schema version (2), unique invocation ID, absolute project root |
| status | running, succeeded, failed, or cancelled |
| started, finished, durationMs | UTC timestamps and wall-clock duration in milliseconds; durationMs is 0 while running |
| error | One-line failure summary, at most ~300 characters and never the full command line. It is the first parsed diagnostic formatted `file:line[:column]: message`, or the compacted error text when no diagnostic was parsed. Empty on success |
| diagnostics | Array of failure diagnostics; an empty array on success, never null. Each entry has `severity` (error, warning, note), `code` (VMAKE_E_COMPILE, VMAKE_E_LINK, VMAKE_E_BUILD, or VMAKE_E_SCRIPT), `message`, and optional `file`, `line`, `column`, `package`, `target`. Compiler/linker output is parsed from the standard GNU `file:line[:column]: severity: message` form and attributed to the failing target and stage; unparseable command failures produce one fallback diagnostic carrying the output tail. `VMAKE_E_SCRIPT` entries come from build script/API errors and carry the package name |
| summary | Present on a successful build only (omitted on failure/cancellation). `durationMs` repeats the top-level duration; `targetsTotal`, `targetsBuilt`, `targetsUpToDate`, `targetsFailed`; `filesCompiled`, `filesLinked` and `actionsUpToDate` count compile and link actions only (post-link steps, void build callbacks and installation are not actions); `artifactsInstalled` equals the artifact count; `changedFiles` is the sorted, unique list of compiled source paths (`[]` when nothing was compiled). Counts describe the scheduler work of this invocation, so a no-op build has zero compiled/linked files and a one-file incremental build has one of each |
| configFile, configSha256 | Selected `.vmake` filename and SHA-256 of the exact bytes used to resolve configuration; SHA of empty bytes for the unsaved default |
| global, packages | Effective global values, and per-package values for the packages that participated in this build (needed packages, including subgraphs). With `--install`, the separate install manifest also lists every local package in the dependency graph, even if it was not built; its remote entries are limited to installed packages |
| toolchain, mode | Effective main build toolchain and mode; package overrides remain in packages |
| compileDatabase | Absolute path to this build's compilation database, or empty if none was generated |
| targets | Executed default targets: package, target, kind, publishable output paths (including declared post-link outputs), `status`, and `durationMs`. `status` is `built` when the target compiled or linked anything in this invocation, or when it is a `void` target (its build callback always runs); otherwise `up-to-date`. `durationMs` is the target wall time (0 when too fast to measure) and is nonnegative. Non-default targets are never executed, even when another target depends on them, so they are never recorded; default targets built through a subgraph are recorded, but installation walks the main graph and skips subgraph roots, so they normally do not add artifacts. Tests appear only with `--tests` |
| artifacts | Only files actually installed by this invocation, each with package, target, buildPath, installPath, size, sha256. PE shared targets also record their `.dll.a` import library |

On success `vmake build`/`vmake rebuild` prints one summary line to stdout, for example `Build succeeded: 34 targets (1 built, 33 up to date), 1 compiled, 1 linked, 7 installed in 4.9s (buildId=...)`; it is additive to the existing progress and `Build succeeded!`/`Install succeeded!` lines. On failure the same command prints one `Build failed: <error>` line to stdout while the concise `Error:` line and the raw tool diagnostics remain on stderr. With `-q`, buildscript `fmt.Printf`/`print` output is suppressed so the summary line is the only stdout; stderr is unchanged (compiler warnings and errors still stream). The summary intentionally excludes post-link, `void` callback and installation actions; it is a scheduler-work summary, and `targets[]` carries per-target status.

The full failing command and raw tool output are deliberately no longer stored in the report: the raw compiler/linker diagnostic remains on stderr (streamed exactly once), and the report carries the parsed form plus the concise summary. On failure the final human `Error:` line on stderr is the same concise summary as `error`. A link or other command failure whose output has no parseable `file:line:column: severity:` prefix yields one fallback diagnostic whose message is the trimmed output tail (up to 1000 characters) with the stage-derived code, and its summary is truncated to the same ~300-character budget.

Artifact paths are absolute, and every artifact has a nonempty installPath. An extra `AddInstalls` file may have an empty target. The artifact list comes exclusively from the invocation's installer records: installed main outputs, declared post-link outputs, SDK public includes and extra files are included. vmake does not create a main output file for a `TargetVoid` target, so installation normally returns before installing its declared post-link outputs even though they appear in targets. Directories contribute only files that passed the installer filter in this invocation; stale destination files are excluded. `installPath` is not necessarily under the global prefix: a package's `InstallContext.SetPrefix` redirects its artifacts, and installation only clears the global `--prefix` (default `install/`), not custom prefixes. Source and installed bytes must have matching SHA-256 identities. The build context is reused without a second OnBuild invocation or build-key reconstruction. Incremental no-op builds with installation still publish a fresh build ID and verify installed file identities. Without `--install`, artifacts is an empty array even if a previous installation remains on disk; configuration, targets and the compilation database are still reported.

The main output of an `object` target is an intermediate link input. It is excluded from the target's published outputs, including prebuilt object targets. An object target with no declared post-link outputs therefore has an empty output list. Compilation and linking still use its object file normally. Other executed default targets retain their output paths in targets for build metadata, but uninstalled outputs never become artifacts. Runtime installation skips static-library targets, so their `.a` main output and declared post-link outputs are not installed as target artifacts; `--install-type sdk` includes libraries that are actually installed. Test targets and targets marked `NoInstall` are not installed either. No extension-based display filter is needed by consumers.

A running record replaces the previous success before configuration/build work starts, under the normal project storage lock. Configuration identity is captured from the same bytes that were parsed, and rechecked after build/install. Success requires build, declared post-link outputs, installation and result collection to complete. Failure/cancellation clears artifacts. Panic unwinding cannot publish success before collection finishes. Termination before the running record reaches disk, or a failed first write, can leave the preceding report in place; buildId, configSha256 and artifact sha256 identify whether it belongs to the invocation being watched. clean/distclean and `pkg clean` invalidate the report before cleanup.

Consumers must require status=succeeded, matching project/configuration, and verify selected artifacts against sha256 before executing them. A report proves the outputs of a particular completed build; it does not assert that all source files are unchanged since that build. Keep buildId when correlating tasks, and do not infer freshness from installed directory contents. Reports use schemaVersion 2; the version 1 fields keep their meaning, and consumers pinned to schemaVersion 1 must accept the new version.
