# Structured build results

`vmake build` (including bare `vmake`, `build -iV`) and `vmake rebuild` atomically publish `build/vmake-build.json`; `vmake test` publishes its own `build/vmake-test.json`. The two documents use the same schemaVersion 2 shape but are written by separate invocations: a test run never rewrites the build report, so the last successful build state survives passing, failing, no-test and preflight-failed test runs. These files are separate from the dependency version manifest in the install directory. Build scripts do not declare hardware or IDE configuration.

The version 2 JSON object contains all version 1 fields plus `durationMs`, `diagnostics`, `command`, `tests`, report provenance (`vmakeVersion`/`vmakeCommit`, and `projectRevision`/`projectDirty` in a git worktree), and (when results were collected) `summary`, and `error` is now a concise one-line summary:

| Field | Meaning |
| --- | --- |
| schemaVersion, buildId, root | Schema version (2), unique invocation ID, absolute project root |
| status | running, succeeded, failed, or cancelled. For `vmake test`, succeeded means every executed test target passed and also covers a host project with no test targets; failed means at least one test failed, `--require-tests` found no runnable test target, or the test preflight/build refused or failed. A keep-going (`-k`) build failure stays failed even when surviving test binaries execute and pass; the build error remains primary |
| command | `build` for a build, `rebuild` for `vmake rebuild`, and `test` for `vmake test`; a missing value means `build` in reports written before this field existed |
| started, finished, durationMs | UTC timestamps and wall-clock duration in milliseconds; durationMs is 0 while running |
| error | One-line failure summary, at most ~300 characters and never the full command line. It is the first parsed diagnostic formatted `file:line[:column]: message`, or the compacted error text when no diagnostic was parsed. Empty on success |
| diagnostics | Always an array, never null. On success it holds the warnings emitted by the run (an empty array when there were none); on failure it holds the parsed errors first, then warnings. Each entry has `severity` (error, warning, note), `code` (`VMAKE_E_COMPILE`, `VMAKE_E_LINK`, `VMAKE_E_BUILD`, `VMAKE_E_SCRIPT`, or `VMAKE_E_TEST` for errors; `VMAKE_W_TOOL` for warnings), `message`, and optional `file`, `line`, `column`, `package`, `target`. A `vmake test` failure without a build diagnostic (a failed test, `--require-tests` with no runnable test target, or a test preflight refusal) gets exactly one `VMAKE_E_TEST` error entry carrying the same concise message as `error`; per-test details stay in `tests[]`. Error output is parsed from the standard GNU `file:line[:column]: severity: message` form, and GNU ld's `file:line: undefined reference to ...` / `file:line: multiple definition of ...` lines (with an optional `(section+offset)` annotation before the message) are parsed as located errors; all are attributed to the failing target and stage. Unparseable command failures produce one fallback diagnostic whose message prefers the last undefined-reference/multiple-definition line, then the last `error:` line, and only then the raw output tail. `VMAKE_E_SCRIPT` entries come from build script/API errors and carry the package name. Warnings are parsed from the stderr streamed during the build phase only: the capture is cut before test binaries run, so test program stdout/stderr (including the stdout redirect used by `--json`) never becomes a `VMAKE_W_TOOL` warning, while build-phase warnings and a failure before test execution keep theirs. Parsing accepts GNU `file:line[:column]: warning: message` lines as located warnings, and generic `warning: message` or `tool: warning: message` lines become unlocated warnings. Located CMake headers are recognized too: `CMake Warning`, `CMake Deprecation Warning`, `CMake Dev Warning`, `CMake Author Warning`, the legacy `CMake Warning (dev)` form, and `CMake Error`, each followed by `at file:line (context):`. A located header collects its contiguous indented detail lines (blank lines between indented CMake detail are included; collection stops at a non-indented trailer) into one bounded message of at most 1000 characters, preserving `file` and `line`; all warning variants get severity `warning` and code `VMAKE_W_TOOL`. Bare `CMake Warning:`/`CMake Error:` headers collect detail the same way. They are deduplicated (same file/line/column/message) and capped at 50 entries, never affect `status`/`error`, and are not repeated on stderr; the raw warning remains streamed exactly once. Warnings parsed from a failing command keep their package/target attribution, while warnings captured from earlier successful commands carry only `file`/`line`/`column` when the tool emitted them |
| summary | Present whenever results were collected: on success for build/rebuild, on a failed build or test whose scheduler produced a partial result, for `vmake test` after the build phase so test counts remain readable, and for both outcomes of the no-tests preflight (succeeded with `testsFound: 0`, or failed `--require-tests` with `testsFound: 0` and no build). It is omitted when the failure happened before any target was scheduled (for example a buildscript error), except for the no-tests `--require-tests` failure, which keeps a zero-target summary. `durationMs` repeats the top-level duration; `targetsTotal`, `targetsBuilt`, `targetsUpToDate`, `targetsFailed`; `testsFound` counts discovered test targets (executed and not run), while `testsPassed` and `testsFailed` count executed entries only; all three are always present (zero for build/rebuild). Targets recorded as not run do not increase `testsFailed`; `filesCompiled`, `filesLinked` and `actionsUpToDate` count compile and link actions only (post-link steps, void build callbacks and installation are not actions); `artifactsInstalled` equals the artifact count; `callbacks` counts executed `void` targets whose `status` is `built` (their callbacks always run); on a succeeded report `noOp` is true exactly when `filesCompiled == 0`, `filesLinked == 0` and `changedFiles` is empty, so a no-op may still have run callbacks and installed artifacts; `changedFiles` is the sorted, unique list of compiled files recorded as `package:relative/path` with slash separators (`[]` when nothing was compiled; an entry that is already absolute or package-qualified is kept as-is without a second prefix). On a partial failure the counts describe the work attempted before the failure, `targetsFailed` is the number of distinct failed target names in the diagnostics (or 1 when a target failure is known without a name), and `artifactsInstalled` is 0. A failed report never carries `noOp: true`: when a failure would otherwise look like no work (for example a failed `void` callback or CMake configure error before any compilation), `noOp` is recorded as false, even when `targetsFailed` stays 0 because no target name is known. Counts describe the scheduler work of this invocation, so a no-op build has zero compiled/linked files and a one-file incremental build has one of each |
| configFile, configSha256 | Selected `.vmake` filename and SHA-256 of the exact bytes used to resolve configuration; SHA of empty bytes for the unsaved default |
| global, packages | Effective global values, and per-package values for the packages that participated in this build (needed packages, including subgraphs). `global` is populated as soon as configuration is resolved, so a failed report still identifies the attempted configuration. With `--install`, the separate install manifest also lists every local package in the dependency graph, even if it was not built; its remote entries are limited to installed packages |
| toolchain, mode | Effective main build toolchain and mode; package overrides remain in packages |
| vmakeVersion, vmakeCommit | Version string and abbreviated VCS commit embedded in the running vmake binary (`dev`/`unknown` when built without module version or VCS metadata). They are captured when the running report is first written and kept unchanged by finish and partial updates, so a report identifies the binary that produced it |
| projectRevision, projectDirty | Full git HEAD of the project's git worktree and whether the project tree had uncommitted changes when the report was begun. `projectDirty` is present (true or false) whenever the revision is; both are omitted when the project root is not in a supported git worktree or git cannot answer. The scan runs `git status --porcelain` at report start and excludes vmake's own state/output directories (`build/`, `install/`, `.vmake/_locks/`, `.vmake/layout`, `.vmake/vmake.lock`, `.vmake_deps/`, `vmake_deps/`), so later build output never changes it; any other untracked file, including source, counts as dirty. These are recorded observations for comparison and hand-off, not security attestations or signatures |
| compileDatabase | Absolute path to the compilation database, or empty if none was generated. It is recorded whenever the file exists, including on a failed build |
| targets | Executed default targets: package, target, kind, publishable output paths (including declared post-link outputs), `status`, and `durationMs`. On a failed build the array keeps the targets that completed before the failure; the failing target is identified by `diagnostics[].target` and counted by `summary.targetsFailed`. A failure outside target execution (for example a package-level `OnBuild` CMake configure failure) is package-scoped: no target callback ran, so `diagnostics[].target` stays empty and `targets[]` may stay empty; vmake does not invent a target attribution for it. `status` is `built` when the target compiled or linked anything in this invocation, or when it is a `void` target; otherwise `up-to-date`. A `built` `void` target means its callback ran, not that any file was produced. `durationMs` is the target wall time (0 when too fast to measure) and is nonnegative. Non-default targets are never executed, even when another target depends on them, so they are never recorded; default targets built through a subgraph are recorded, but installation walks the main graph and skips subgraph roots, so they normally do not add artifacts. Test targets appear only for `vmake build --tests` and `vmake test` |
| tests | Always an array. Empty for build/rebuild, for a `vmake test` whose build phase failed without `-k`, and for a no-tests preflight (the build is skipped); otherwise one entry per discovered test target. An executed entry has `name` (`package:target`), `package`, `target`, `passed`, `elapsedMs`, `exitCode` (0 on success, the process exit code on failure, -1 when a signal terminated it, 1 when the code is unavailable), `signal` (omitted unless a signal terminated the process; platform wording such as `segmentation fault` or `killed`) and `output` (the combined stdout/stderr tail captured for that test, bounded to 4096 bytes; when longer it starts with `...[truncated]`). After a keep-going (`-k`) build failure, declared test targets that did not run get `notRun: true` plus `skipReason` (`build failed`, `target not built`, `binary missing`, or `unsupported platform`) and keep `passed: false` with zero `elapsedMs`, `exitCode`, and no `signal`/`output`; executed entries keep their normal fields. Partial mode runs a test target only when this invocation recorded it as `built` or `up-to-date` in `targets`; a binary left by an earlier build is never executed and is recorded as `target not built`. Test entries never contain vmake's own `PASS`/`FAIL` progress lines |
| artifacts | Only files actually installed by this invocation, each with package, target, buildPath, installPath, size, sha256. PE shared targets also record their `.dll.a` import library |

`targetsBuilt` counts target records with status `built`, including `void` targets whose callbacks always run; `noOp` can be true while `targetsBuilt` is nonzero (for example eight callback targets).

On success `vmake build`/`vmake rebuild` prints one summary line to stdout (or one JSON envelope with `--json`; see **Machine-readable invocation** below). The normal form is `Build succeeded: 34 targets (9 built, 25 up to date), 1 callbacks, 1 compiled, 1 linked, 7 installed in 4.9s (buildId=...)`, with the `N callbacks` part present only when at least one `void` target callback ran. When nothing was compiled or linked the line reads `Build succeeded: no compilation (34 targets, 26 up to date, 8 callbacks, 7 installed) in 5.0s (buildId=...)`, which makes a true no-op unambiguous. The summary is the only success line: the pipeline no longer prints a separate `Build succeeded!` line, so a successful run ends with exactly one summary (`vmake build --install` still prints `Install succeeded!` after the build phase). On failure the same command prints one `Build failed: <error>` line to stdout while the concise `Error:` line and the raw tool diagnostics remain on stderr. With `-q`, buildscript `fmt.Printf`/`print` output is suppressed so the summary line is the only stdout; stderr is unchanged (compiler warnings and errors still stream). The `filesCompiled`/`filesLinked` counts intentionally exclude post-link, `void` callback and installation actions; callbacks are counted separately and `targets[]` carries per-target status.

`vmake test` writes the same schema with `command:"test"` to `build/vmake-test.json`; it never rewrites `build/vmake-build.json`. The running test record replaces any previous test report before configuration work, and a completed test report carries the build targets, summary, `tests[]` and compilation database from its own build phase when that phase ran. A later failing test run overwrites an earlier succeeded test report with a new buildId, while the build report keeps the previous build's identity. Host projects with no runnable test target succeed by default: after configuration is bound, `vmake test` performs a cheap dry-run target inspection (the same declaration path as `query targets`) and skips the build phase entirely when it declares no default binary test target. The report records `summary.testsFound: 0`, zero target counts, `status: "succeeded"`, `targets: []`, and exits 0 with a `Tests succeeded: no test targets` summary; no compilation, link, installation, build-key directory or compilation database is produced. `--require-tests` turns that case into a failure before the build with the concise error `no test targets found`, one `VMAKE_E_TEST` diagnostic, a summary with `testsFound: 0`, and exit 1. The no-tests preflight falls back to the normal build path when the inspection cannot be trusted (missing or unmaterialized package source, script or target-declaration error, toolchain or configuration error), preserving the build-then-discover behavior and its errors. The no-tests preflight runs before the platform check and skips the build when it can trust the declared target set and finds no runnable test. When runnable tests exist, the platform preflight refuses a project whose effective root platform cannot run native tests (`target_os` is `none`, differs from the host, or `target_triple` is non-empty) before any build action: it writes a failed test report with the `cannot run tests for project target ... use 'vmake build --tests'` error, preserves the build report, and does not create build-key directories or the compilation database. `vmake build --tests` is still a build: zero test targets is not an error there and its test counts stay zero. Test reports keep `summary` on test failure because the build phase completed; when the build phase itself fails, the failed report keeps the completed targets and partial summary collected before the failure, and still carries the resolved configuration identity, packages and compilation database. With `-k`, that failed report also executes the test binaries this invocation built successfully (targets recorded `built` or `up-to-date`); a stale binary from an earlier build is never executed and is recorded as `target not built`. Executed entries keep their normal test fields, declared test targets that did not run are recorded with `notRun` and a `skipReason`, `summary.testsFound` counts both, and the build error remains the report's `error` and the command's exit status. Without `-k`, a build-phase failure records no test entries and runs no tests. `summary` is omitted only when the failure prevented any target from being scheduled, such as a buildscript error or the platform preflight refusal; the no-tests `--require-tests` failure keeps a summary with `testsFound: 0`. The no-tests success report is a skipped build, so `targetsTotal`, `filesCompiled` and `filesLinked` are 0 and `noOp` is true. `vmake test` never installs outputs, so `artifacts` is empty. It prints `Tests succeeded: <passed>/<found> passed in <duration> (buildId=...)` on success, `Tests succeeded: no test targets (buildId=...)` when none were declared, and `Tests failed: <error>` on failure; with `-q` that is the only stdout, and in `--json` mode the envelope replaces both lines (see **Machine-readable invocation**). The report is the single overall test summary: per-test `PASS`/`FAIL` lines still print, but there is no separate `N/M test(s) passed` stdout line. Test `PASS`/`FAIL` progress and child output keep streaming as before; the captured `tests[].output`, `tests[].exitCode` and `tests[].signal` are report data only. Test program output is never parsed as a build warning because the stderr warning capture is cut before tests run. Test binaries execute with their working directory set to the package's `BuildDir()` (the directory that contains the test executable), so relative paths in a test program resolve there. A signaled test records `exitCode: -1` with the platform signal name in `signal`.

## Console output

The default view keeps progress that carries new information: compile/link/generate/install action lines, buildscript prints, and the final summary. Per-target `[package:target]` headers are detail and print only with `-v`; the report and `changedFiles` carry the package/target context at default. `-v` restores the headers together with the build order and the full captured CMake logs.

`Downloading package sources...` is printed only when at least one needed source actually needs materialization or a remote resolve; a no-op build does not print the heading. CMake helper output is captured instead of streamed raw. `CMakeConfigure` prints one `cmake configure: done` line at default (or `cmake configure (cached): <dir>` when its fingerprint is unchanged), and `CMakeBuild`/`CMakeInstall` print their step or installed/up-to-date counts. CMake's `-- ...` configure scaffolding, Ninja progress and `-- Up-to-date` install lines are hidden from the default view (the captured log stays available with `-v`); Ninja steps and install counts are summarized. CMake warning and error lines, including compiler `file:line: warning:` diagnostics from the build stage, stream to stderr rather than stdout, so the warning capture can report compiler-style warning lines as `VMAKE_W_TOOL` entries at default and with `-q`. `-v` additionally prints the full captured CMake log; `-q` prints nothing on stdout for a successful configure (the summary is its only default line) while warnings and errors still reach stderr. A CMake stage running longer than 10 seconds prints `  cmake <stage>: still running (Ns)` to stderr every 10 seconds (including under `-q`), so a captured long build is not silent; fast stages print no heartbeat.

## Build check (plan mode)

`vmake build --check` (alias `--plan`) reports what the next build would do without doing it. It resolves the project exactly like a build: dependency resolution, `OnConfig`/`OnRequire`/`OnBuild` callbacks, source preparation and toolchain resolution all run, so buildscript callbacks can still write files and check can materialize sources or update `.vmake/vmake.lock`. It then evaluates the same action signatures and action records a build uses, but skips generator rules and config-header generation, object/install directory creation, compiler and linker invocation, `void` target callbacks, post-link steps, prebuilt realization, artifact publishing/installation, action-record writes or invalidation, and the compilation database.

A compile or link action whose signature and inputs match a previous build counts as up to date. A pending compile is reported once per source file, and its target's link is reported as pending too (the object will change). A target that depends on a target planning to replace its artifact is also reported as a pending link even though its own recorded inputs are unchanged. `void` callbacks always run in a build, so they are counted as planned callbacks and do not make `workPending` true by themselves (`workPending` is `plannedCompiles + plannedLinks > 0`). A default target counts once in `plannedGenerators` when it declares generator rules or its package enables a generated config header, even when the target declares several rules; check never runs generation.

Check does not write `build/vmake-build.json`, `build/compile_commands.json`, object files, libraries, installed files or `build/vmake-test.json`, and it never installs. A real build clears stale remote-package install staging directories before building; check leaves them untouched, so an existing published dependency library is treated as current.

Check exits 0 when planning succeeds, regardless of pending work; 1 on resolution/planning errors; and 2 for usage errors, including `--check` combined with `--install` or `--tests` (`--check --install` does not install, and test targets are not planned).

Human output is one line on stdout; pipeline progress and buildscript prints go to stderr (and are suppressed by `-q`):

```
Build check: 2 compiles, 2 links, 1 callback pending (0 actions up to date)
Build check: 1 compile, 1 link pending (0 actions up to date); 1 generated-input target(s) not checked
Build check: up to date (no compile/link work; 1 callback would run)
Build check: up to date (no compile/link work); 2 generated-input target(s) not checked
Build check: up to date (no compile/link work)
```

When `plannedGenerators` is nonzero, the pending and up-to-date forms of the line end with `; N generated-input target(s) not checked`.

On failure the line is `Build check failed: <concise error>` and the human error stays on stderr. `--json` (or `--output PATH`) emits exactly one document on stdout instead:

```json
{
  "schemaVersion": 1,
  "command": "check",
  "status": "ok",
  "data": {
    "workPending": true,
    "plannedCompiles": 2,
    "plannedLinks": 2,
    "plannedCallbacks": 1,
    "plannedGenerators": 1,
    "caveats": ["generator rules/config headers are not executed; targets depending on generated inputs may be undercounted"],
    "upToDate": 0,
    "targetsTotal": 3,
    "vmakeVersion": "1.0.77",
    "vmakeCommit": "ef9d2f79"
  },
  "diagnostics": []
}
```

| Field | Meaning |
| --- | --- |
| schemaVersion, command, status | Envelope schema 1, `check`, and `ok` or `error` |
| workPending | `plannedCompiles + plannedLinks > 0`; planned callbacks alone keep it false |
| plannedCompiles | Pending compile actions, one per source file whose action signature/inputs do not match |
| plannedLinks | Pending link actions (including targets whose compile or dependency artifact will change) |
| plannedGenerators | Default targets with generator rules or in a package with a generated config header, counted once per target; generation is not executed |
| caveats | Human-readable caveat strings; one entry when `plannedGenerators > 0`, omitted otherwise |
| plannedCallbacks counts default `void` targets with a BuildFunc or post-link steps; the report `callbacks` count is executed `void` targets recorded built and can differ. |
| plannedCallbacks | Default `void` targets whose build callback or post-link steps would run |
| upToDate | Compile/link actions verified up to date, the same action count as a build report's `actionsUpToDate` |
| targetsTotal | Default, non-test targets in the plan (including `void` targets) |
| vmakeVersion, vmakeCommit | Version and abbreviated VCS commit of the running vmake binary, stamped onto every check data object. Check does not write a build report, so this is the only binary identity its document carries; no project revision/dirty scan is performed |
| diagnostics | Always an array. On error the parsed error diagnostics, or one `VMAKE_E_BUILD` fallback; `data` is `null` on error |

Check is a plan, not a guarantee: generator rules and generated config headers are not executed, so targets whose sources are generated can be undercounted and a generated header is only reflected through the previous build's depfile; header changes are detected only for headers recorded in a dependency file (never-compiled headers are invisible); artifacts produced by `void` callbacks are not predicted; and up-to-date decisions require action records from a previous build. File contents are compared by hash, so reverting edited content or a comment-only `build.go` edit does not leave work pending. `--explain` is accepted and adds no per-action reasons to the plan output.

## Machine-readable invocation

`vmake build --json`, `vmake rebuild --json` and `vmake test --json` write exactly one JSON document to the real stdout when the command finishes. `--output PATH` (see **Output file** below) writes the same document to a file instead:

```json
{
  "schemaVersion": 1,
  "command": "build",
  "status": "ok",
  "reportPath": "/abs/project/build/vmake-build.json",
  "installManifest": "/abs/project/install/manifest.json",
  "invocation": "build",
  "data": { "schemaVersion": 2, "buildId": "...", "status": "succeeded", "...": "..." },
  "diagnostics": []
}
```

| Field | Meaning |
| --- | --- |
| schemaVersion | Envelope schema version, currently 1 |
| command | `build` for a build, `rebuild` for `vmake rebuild`, `test` for `vmake test` |
| status | `ok` when the report status is succeeded; `error` when it is failed or cancelled |
| reportPath | Absolute path of the report this invocation published (or would publish): `<root>/build/vmake-build.json` for build/rebuild, `<root>/build/vmake-test.json` for test |
| installManifest | Absolute path of the install manifest for this invocation's installation prefix: `<root>/install/manifest.json` by default, or `<--prefix>/manifest.json` when an install prefix override is given. It is emitted for every invocation, including build/test runs that do not install |
| invocation | The command that produced the document: `build`, `rebuild`, or `test`; equal to `command` |
| data | The complete schemaVersion 2 report described above, identical to the file named by `reportPath` (`build/vmake-build.json` or `build/vmake-test.json`) |
| diagnostics | A copy of `data.diagnostics`; always an array. On success it therefore carries the collected `VMAKE_W_TOOL` warnings even when `-q` suppressed stderr progress |

`reportPath`, `installManifest` and `invocation` are invocation metadata and are not added to the on-disk report; the envelope is the self-locating document a machine consumer should keep. `vmake rebuild --json` reports `command`, `invocation` and `data.command` as `rebuild`, while its human success line stays a build summary. `vmake test --json` keeps `data` identical to `build/vmake-test.json`; the build report is untouched, so a consumer watching test results must use `reportPath`, not a hard-coded build path.

While the command runs, vlog progress, buildscript `fmt`/`print` output, child-process stdout and other human text go to stderr instead of stdout. Raw compiler/linker output and the concise final `Error:` line remain on stderr, and JSON mode does not print the human success/failure summary line at all, so `vmake build --json | jq .status` is safe. `--json` does not change the report file, artifacts or exit codes: a failed run still exits non-zero after emitting `status:"error"` with the concise `data.error` and diagnostics. `-q`, `-v` and `-V` keep controlling stderr verbosity; with `-q`, buildscript stdout stays suppressed as in normal quiet mode, while the JSON document is still written to stdout.

### Output file

`vmake build|rebuild|test --output PATH` implies `--json` and writes the JSON envelope to `PATH` instead of stdout; stdout stays empty. Human progress, raw diagnostics and the final `Error:` line go to stderr exactly as in `--json` mode. A relative `PATH` resolves against the process working directory, and `--output -` is equivalent to `--json` (stdout). When both `--json` and `--output` are given, the file wins and nothing is written to stdout. The parent directory must already exist; vmake does not create it. The document is written to a temporary file in the destination directory and renamed into place, so a consumer never reads a half-written envelope. A write failure (for example a missing parent directory) is a clean error on stderr and the run exits 1 even when the build itself succeeded; the report under `build/` is unaffected. `--output` is accepted only by `build` (including `--check`), `rebuild` and `test`.

### Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Success, including `--help`, `version`, and a successful `build --check` (even when the plan reports pending work) |
| 1 | Operation failure: compile/link/buildscript/test failure, `build --check` resolution/planning failure, no test targets with `--require-tests`, test preflight refusal, report or result-write failure, storage failure |
| 2 | Usage or project-resolution failure: unknown/invalid flag, missing required argument, not inside a vmake project |
| 130 | Interrupted by SIGINT |
| 143 | Interrupted by SIGTERM (non-Windows) |

The exit code does not depend on `--json`/`--output`; the requested envelope is emitted before the process exits with the code above. Ordinary build, script and test failures are never reported as 2.

### Errors before the report exists

When `--json` or `--output` was requested but the invocation fails before the normal envelope can be produced (flag-parsing error, not inside a vmake project, storage-lock acquisition, or another pre-report failure), vmake still emits exactly one generic envelope:

```json
{
  "schemaVersion": 1,
  "command": "build",
  "status": "error",
  "data": null,
  "diagnostics": [
    { "severity": "error", "code": "VMAKE_E_USAGE", "message": "unknown flag: --nope" }
  ]
}
```

`command` is the first non-flag argument when it is `build`, `rebuild` or `test`; other invocations get no document. `data` is `null`, and `reportPath`, `installManifest` and `invocation` are omitted. The diagnostic code is `VMAKE_E_USAGE` for usage/project-resolution errors and `VMAKE_E_BUILD` for other failures. The human error is still printed once on stderr. The request is detected from the raw command line so it works even when flag parsing fails; an invocation that reaches the normal report path emits only that envelope (never both). The generic envelope is not produced for `--help`/`version`, and `--json --output PATH` writes it to PATH with stdout empty.

The full failing command and raw tool output are deliberately no longer stored in the report: the raw compiler/linker diagnostic remains on stderr (streamed exactly once), and the report carries the parsed form plus the concise summary. On failure the final human `Error:` line on stderr is the same concise summary as `error`. A link or other command failure whose output has no parseable location yields one fallback diagnostic with the stage-derived code; its message prefers the last `undefined reference`/`multiple definition` line, then the last `error:` line, and only then the trimmed output tail (up to 1000 characters), and its summary is truncated to the same ~300-character budget. GNU ld's `file:line:(section): undefined reference to ...` and `multiple definition of ...` lines are parsed as located errors, so a link failure summary names the source location and the unresolved symbol instead of a build-key path prefix.

Artifact paths are absolute, and every artifact has a nonempty installPath. An extra `AddInstalls` file may have an empty target. The artifact list comes exclusively from the invocation's installer records: installed main outputs, declared post-link outputs, SDK public includes and extra files are included. vmake does not create a main output file for a `TargetVoid` target, so installation normally returns before installing its declared post-link outputs even though they appear in targets. Directories contribute only files that passed the installer filter in this invocation; stale destination files are excluded. `installPath` is not necessarily under the global prefix: a package's `InstallContext.SetPrefix` redirects its artifacts, and installation only clears the global `--prefix` (default `install/`), not custom prefixes. Source and installed bytes must have matching SHA-256 identities. The build context is reused without a second OnBuild invocation or build-key reconstruction. Incremental no-op builds with installation still publish a fresh build ID and verify installed file identities. Without `--install`, artifacts is an empty array even if a previous installation remains on disk; configuration, targets and the compilation database are still reported.

The main output of an `object` target is an intermediate link input. It is excluded from the target's published outputs, including prebuilt object targets. An object target with no declared post-link outputs therefore has an empty output list. Compilation and linking still use its object file normally. Other executed default targets retain their output paths in targets for build metadata, but uninstalled outputs never become artifacts. Runtime installation skips static-library targets, so their `.a` main output and declared post-link outputs are not installed as target artifacts; `--install-type sdk` includes libraries that are actually installed. Test targets and targets marked `NoInstall` are not installed either. No extension-based display filter is needed by consumers.

A running record replaces the previous success of the same document before configuration/build work starts, under the normal project storage lock: build/rebuild rewrites `build/vmake-build.json` and test rewrites `build/vmake-test.json`. Configuration identity is captured from the same bytes that were parsed, and rechecked after build/install. Success requires build, declared post-link outputs, installation and result collection to complete; `vmake test` additionally requires every executed test to pass, while a host project with no runnable test target succeeds unless `--require-tests` is passed. A project whose effective root platform cannot execute tests fails the platform preflight before the build starts. The no-tests preflight runs before the platform check and, when it can trust the declared target set, skips the build phase; it writes the succeeded or `--require-tests`-failed test report without touching the build report. Failure/cancellation clears artifacts. A build or build-phase failure also publishes the partial result: the completed targets, package values, configuration identity, compilation database and a summary whose counts cover the work attempted before the failure, with `targetsFailed` counting distinct failed target names. That partial summary is omitted when the failure happened before scheduling, and installation is never attempted after a build-phase failure. For `vmake test`, a test failure after the build phase keeps the full build summary so the test counts remain readable; a `--require-tests` no-tests failure keeps a zero-target summary, and a default no-tests success records `testsFound: 0` with status succeeded. When runnable tests exist, the platform preflight refusal happens before scheduling, so its failed report has no summary and no build targets; it and the no-tests preflight path leave the build report intact. Panic unwinding cannot publish success before collection finishes. Termination before the running record reaches disk, or a failed first write, can leave the preceding report in place; buildId, configSha256 and artifact sha256 identify whether it belongs to the invocation being watched. clean/distclean and `pkg clean` remove both `build/vmake-build.json` and `build/vmake-test.json` before cleanup. `vmake clean` also removes the now-stale `build/compile_commands.json`; when build-key directories for other configurations remain, it prints one note with their count and a suggestion to use `vmake clean --all` or `vmake distclean`, and leaves those directories in place.

Consumers must require status=succeeded, matching project/configuration, and verify selected artifacts against sha256 before executing them. A report proves the outputs of a particular completed build; it does not assert that all source files are unchanged since that build. Keep buildId when correlating tasks, and do not infer freshness from installed directory contents. Reports use schemaVersion 2; the version 1 fields keep their meaning, and consumers pinned to schemaVersion 1 must accept the new version.
